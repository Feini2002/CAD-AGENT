# CAD Agent 决策记录

> 本文已从根目录迁入 `docs/decisions/`。它记录“为什么这样做”，不承载当前执行计划；当前唯一 PlanMD / 主计划是根目录 `CORE_RESTRUCTURE_PLAN.md`。

这个文件记录“为什么这样做”。如果未来改方向，先看这里，避免重复讨论。

## D001：使用 CAD_PLAN 作为中间层

日期：2026-05-24

决策：

用户白话不能直接进入 CAD 绘制，必须先转换成结构化 `CAD_PLAN`。

原因：

- 白话有歧义。
- JSON 可以校验、保存、复用、回放。
- 脚本更适合执行结构化计划，而不是理解自然语言。
- 以后住宅家装、商业工装、零售店铺、办公空间、餐饮空间、展厅展陈等场景都能复用同一套流程。

影响：

- 每个绘图功能都要先写 CAD_PLAN 示例。
- 后续脚本优先围绕 CAD_PLAN 开发。

## D002：先使用文件记录，不先使用 SQL

日期：2026-05-24

决策：

当前不引入 SQL 数据库，先用 Markdown、JSON、Python 脚本推进。

原因：

- 当前阶段重点是跑通最小闭环。
- 文件更直观，用户容易打开阅读。
- SQL 会增加维护成本，暂时没有必要。

影响：

- 进度记录用 Markdown。
- 配置和计划用 JSON。
- 等对象库、项目记录复杂后，再评估是否需要数据库。

## D003：先不创建根目录 AGENTS.md

日期：2026-05-24

决策：

暂时不在总根目录创建 `AGENTS.md`。

后续状态：

该决策已被后续阶段取代。2026-05-25 已创建根目录 `AGENTS.md`，并把它作为 Codex 默认规则入口。此处保留作为历史记录，说明早期为何没有立即固化全局规则。

原因：

## D004：本文件夹定位为可迁移通用开发包

日期：2026-05-24

决策：

`CAD测试相关文件` 不是当前家装图纸的专用资料夹，而是一个可迁移的通用 CAD Agent 开发包。

原因：

- 用户希望未来复制该文件夹到其他电脑后，可以恢复同一套开发状态。
- 用户希望该能力适用于家装、工装、店铺、办公、餐饮等不同 CAD 场景。
- 具体项目图纸、路径、房间名称、坐标和图层应放在项目上下文里，不应写死到通用规则中。

影响：

- README、规则、状态和 Skill 文案必须使用通用表达。
- 当前电脑的 AutoCAD 测试结果只能作为环境验证记录。
- 后续新增对象库和行业包时，优先保持可扩展，而不是只服务单一项目。

## D005：卡壳自查作为横向机制

日期：2026-05-25

决策：

把“卡壳时如何自查、截图、复现、修复和记录”作为横向机制，而不是绑定到某一个开发阶段。

原因：

- 阶段 4 预览绘制会遇到画不准、画不出来的问题。
- 阶段 5 回读验证、阶段 6 对象库、阶段 7 行业包也会遇到类似卡点。
- 如果只写在某个阶段里，后续容易忘记复用。

影响：

- 新增 `CAD_AGENT_BLOCKER_PLAYBOOK.md` 作为统一入口。
- 后续任意阶段出现卡壳，都先运行自检、保留证据、定位层级，再做最小修复。
- 视觉类问题默认需要截图或明确说明无法截图的原因。

## D006：仓库重心调整为通用 CAD Agent Core Lab

日期：2026-05-25

决策：

将 `CAD测试相关文件` 的长期定位从“通用 CAD Agent 开发包”进一步明确为“通用 CAD Agent Core Lab”。后续开发优先沉淀通用 Core，场景 Agent 只作为轻量配置层。

原因：

- 用户希望未来支持工装、家装、办公、餐饮、展陈等多个场景，而不是把仓库写死成工装 Agent。
- 用户希望多数能力可复用，例如对象生成、风格、图库块、布局、图纸理解、验证和安全。
- CAD-MCP 已提供底层执行能力，本仓库的价值应在通用设计底座和多场景复用。

影响：

- 新增 `CORE_RESTRUCTURE_PLAN.md`、`CORE_STATUS.md`、`CORE_ROADMAP.md`。
- 新建 `core/`、`agents/`、`libraries/`、`projects/` 等结构。
- 旧 `scripts/`、`drivers/` 保留兼容壳，真实实现迁入 Core。
- 场景 Agent 不得复制 Core 能力，只写场景差异。

## D007：使用短上下文入口降低开发抖动

日期：2026-05-25

决策：

新增 `CORE_CONTEXT_BRIEF.md` 作为日常恢复上下文的短入口。普通开发默认先读 `AGENTS.md` 和 `CORE_CONTEXT_BRIEF.md`，再按任务展开 `CORE_STATUS.md`、`CORE_RESTRUCTURE_PLAN.md`、`CAD_AGENT_ISSUES.md` 等详细文件。

原因：

- 当前系统经历深度开发和大型补强，状态文档、计划、changelog、issues 都变长。
- 每轮都全文读取所有历史文档，会增加上下文噪音，也容易让旧阶段口径干扰当前判断。
- 短入口能稳定记录当前结论、安全边界、下一步路线和按需展开表。

影响：

- `CORE_CONTEXT_BRIEF.md` 必须保持短、稳定、可扫读。
- 历史流水继续写入 `CAD_AGENT_CHANGELOG.md`。
- 失败教训继续写入 `CAD_AGENT_ISSUES.md`。
- 主计划继续写入 `CORE_RESTRUCTURE_PLAN.md`。

## D008：`CORE_RESTRUCTURE_PLAN.md` 作为主 plan

日期：2026-05-25

决策：

根目录不新增独立 `plan.md`。当前唯一 PlanMD / 主计划文件为 `CORE_RESTRUCTURE_PLAN.md`；用户提到 `PlanMD`、`plan.md`、主计划或主 plan 时，默认指该文件。

原因：

- 仓库已经有大量根目录 Markdown，再新增同义 plan 文件会增加重复入口。
- `CORE_RESTRUCTURE_PLAN.md` 已承载 Phase 计划、执行边界、验证命令和完成判定。
- 明确映射比复制一份计划更容易维护。

影响：

- `README.md`、`CORE_CONTEXT_BRIEF.md`、`CAD_AGENT_STATUS.md` 和 `CORE_RESTRUCTURE_PLAN.md` 都应保持这个口径。
- 若未来真的创建 `plan.md`，它应是极薄跳转文件，不能复制主计划正文。
