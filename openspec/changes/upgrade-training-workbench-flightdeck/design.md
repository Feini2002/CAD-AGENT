## Context

The current training workbench is built around `capability-map.html` plus `capability-map-data.js`. The data snapshot is generated by `scripts/build_capability_map_data.py`, refreshed by `scripts/sync_training_workbench.py`, and guarded by `scripts/run_training_workbench_agent_check.py`. It already exposes training programs, Agent profiles, Prompt contracts, training sources, model traces, Table C boundary, and sync status.

The page is now too table-first for daily CAD Designer Agent training. The system needs an operator flightdeck that surfaces next actions, source health, gate blockers, Agent dispatch, evidence bundles, and learning feedback without weakening the repository rule that HTML and JS snapshots are derived only.

The repository has a dirty worktree with many existing unrelated changes. This change must avoid reverting or normalizing those changes and should keep edits scoped to the new OpenSpec change plus training workbench files.

## Goals / Non-Goals

**Goals:**

- Make the default workbench view a command center for training decisions rather than a 217-row table.
- Add a schema v3 view model that separates durable facts, indices, and UI-specific views.
- Surface source health, encoding health, data-bloat / evidence closure, Table C boundary, Agent check, and sync freshness as first-class gateboard signals.
- Provide next training candidates with route mode, reason, responsible agents, evidence requirements, and blocking conditions.
- Model Agent / Prompt / Tool / Trace relationships as registered nodes and edges rather than hard-coded UI assumptions.
- Keep the first implementation slice static, local, and framework-free.

**Non-Goals:**

- Do not promote Table C or claim new CAD geometry capability.
- Do not make the browser write repository facts or trigger training silently.
- Do not require a React, Canvas, or live event-stream migration in the MVP.
- Do not embed full reports, screenshots, or large created-handle arrays inside `capability-map-data.js`.
- Do not treat archived training evidence as active pass evidence.

## Decisions

### Decision 1: Keep Static Snapshot, Add Schema v3 View Model

The workbench SHALL keep `window.CAD_CAPABILITY_MAP_DATA = ...` as the compatibility entrypoint. The v3 model will add `meta`, `facts`, `indices`, `views`, and `ui` sections while preserving enough v2 data for current tests and gradual migration.

Alternative considered: make a local API server the source of truth. Rejected for MVP because the repository already relies on deterministic snapshot generation, and the browser must not become a writable authority.

### Decision 2: Command Center First, Table Second

The default active view will become a command center. The training matrix remains available under training map, but the first screen must show next candidates, gateboard health, evidence boundary, latest run state, and Agent dispatch chain.

Alternative considered: keep the current tab order and add a summary banner. Rejected because it leaves the daily operator workflow buried under the old matrix.

### Decision 3: Build Reusable Entity, Gate, Evidence, Graph, and Timeline Models

The data builder will derive reusable entities instead of UI-only string blobs. Training programs, agents, prompt packs, tool contracts, gates, runs, sources, and evidence bundles will carry stable IDs so future scenario agents, asset workflows, Prompt Pack calibration, and Tool Contract traces can be added without rewriting the page.

Alternative considered: hard-code only the current 28 agents and 217 training rows. Rejected because the user explicitly wants a future training flightdeck.

### Decision 4: Treat Realtime as Snapshot Freshness First

The MVP will not claim browser-live training state. It will display snapshot freshness, current run or queue summaries when present, and refresh prompts. Future training event files can be folded into `views.dashboard` and `views.traceViewer` through sync, but the first slice remains event-driven snapshot refresh.

Alternative considered: add a browser live stream immediately. Rejected as risky because it could blur fact-source boundaries and require a server write path.

### Decision 5: Extend Existing Checks Instead of Adding a Parallel Validator

`scripts/run_training_workbench_agent_check.py` will remain the main drift guard. It should be extended to check v3 presence, derived/fact separation, command-center fields, gateboard fields, evidence boundary copy, source health, and HTML hooks.

Alternative considered: add a new independent check script. Rejected for MVP because the current sync chain already expects one agent-check report.

## Risks / Trade-offs

- Large snapshot risk -> keep v3 compact, store summaries and paths only, and test that legacy aliases are not duplicated unnecessarily.
- UI over-claim risk -> render `derived`, `visual_aid_only`, `not_checked`, `archived_only`, and `missing_evidence` as distinct states.
- File split risk -> keep root `capability-map.html` compatible first; only split into `workbench/` after behavior is locked.
- Dirty worktree risk -> avoid broad formatting, avoid deleting untracked output, and review touched files carefully.
- `file://` compatibility risk -> use classic scripts for the first frontend slice; module/fetch-only architecture can wait until local server behavior is stable.
- Visual density risk -> make desktop the primary experience, use compact tables, sticky command bars, and a persistent inspector instead of decorative cards.

## Migration Plan

1. Add v3 data model builders beside the existing v2 output path and expose the new fields in `capability-map-data.js`.
2. Add focused tests for v3 command center, gateboard, source registry, evidence bundles, and Agent graph.
3. Extend the workbench agent check to validate v3 fields and HTML hooks.
4. Rework `capability-map.html` default view into a command center while keeping the existing training, agents, failures, traces, and boundary content available.
5. Add static visual smoke verification after sync.
6. Later, split the HTML/CSS/JS and Python builder into focused modules once v3 behavior is proven.

Rollback strategy: keep v2 fields and existing render paths until the command center and v3 checks pass. If v3 rendering fails, the page can fall back to v2-normalized data and existing views.

## Open Questions

- Whether to introduce `workbench/` split files in this same change or after the command center MVP passes visual verification.
- Whether `nextTrainingCandidates` should initially be purely deterministic or read a future operator-maintained preference file.
- Whether the first Agent graph should render as a CSS grid / SVG-lite view or remain a structured dispatch-chain panel until a second slice.
